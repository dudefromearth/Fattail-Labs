## 1. Band (spec §1) — CONFIRMED

Spec §1, restated from v0.8 §4 so nothing is ambiguous:

- Per book `(symbol, expiry)` at each capture:  
  `σ_T = spot × ATM_IV(expiry) × √(T_σ / 252)`, `T_σ = max(trading_dte, 1)`.
- `follow(t)` = listed strikes inside `spot ± (2.5 + LEAD_SIGMA) × σ_T`, `LEAD_SIGMA` default **0.25**.
- `active(t) = follow(t) ∪ every strike admitted earlier this session for this book` — ratchet; trailing strikes never drop.
- **0DTE included the same way.** Fixed `wings()` count retired for capture. `LABS_SSR_WINGS`, `book_wings()`, `band_scale()`, `lead_wings` retired; `LABS_SSR_BAND_SIGMA` (2.5) and `LABS_SSR_BAND_LEAD_SIGMA` (0.25) replace them. `wings_max` becomes a **σ cap**, default 4.0, safety rail only.
- ATM IV = that book’s own ATM IV from the feed at that capture. Degenerate (`<1%` or `>200%`): hold last good window for that book and log; never collapse.

Plan W1 / seed A1 name the same objects. Analysis v0.1 Part 1 quotes as-built: **no IV, no T, no 2.5σ, no ratchet** — 0DTE is `wings()`, 1–5 DTE is `book_wings(√(1+T))`. That is the gap this spec closes. 0DTE is not a special case.

**India note (not a block; Hotel owns H0):** v0.8 §4.1 writes `follow` at `LABS_SSR_BAND_SIGMA × sigma_estimate × sqrt(T_e) × spot` and a **separate** `lead(t)` with `sqrt(horizon)`. Spec v0.1 folds lead into `(2.5 + 0.25) × σ_T` and names ATM IV of the expiry, not `sigma_estimate(symbol)`. If `horizon = T_e` and ATM IV is the one σ, the capture edge is the same number. v0.8 is **DRAFT — not BUILD AUTHORITY**. DL-797 GOs v0.1. Hotel H0 is the T_σ / IV-hold seat. India does not invent a second estimator (v0.8 §9 / E36).

### As-built interest → Massive

1. Taps **do not call Massive**. They `touch_interest` on `mb:ladder:{SYM}:{exp}:w{N}:dual` (`ssr_live_capture.py` L155–161, L585–587; `ssr_mexp_capture.py` L235–239).
2. `chain_feed.tick()` lists **all** `mb:ladder:` interest and, **serially**, `_fetch_ladder_uncached(..., wings=N)` for each (`chain_feed.py` L44–93). Interval **2s**.
3. Topic identity **is** `w{N}`. Different N = different Redis key = different Massive pull. Same N = shared generation.
4. Live 0DTE looks up `w{wings()}` then 15 then 25. MEXP extra books look up `w{book_wings}` (27–42 with base 15). Analyzer/Labs may also hold `w25` (Monday 0DTE used `w25` because that ladder had rows).

### Why one interest set cannot serve two windows

| If Tuesday parallel… | Live | Archive vs spec §2 | Massive |
|----------------------|------|--------------------|---------|
| Reads **only** live’s `w15`/`w25`/`book_wings` keys | Unchanged | **Subset.** Monday SPX already &lt;2.5σ. W5 would fail. Spec §2 forbids storing a subset because Redis was narrower. | No extra pull |

| **Replaces** live keys with covering N only | Live lookup of w15/w25 **misses** unless Analyzer still holds w25 | Parallel ok; **live starves** | Fewer keys, wrong victim |

**India does not invent a second Massive client.** Arch 28: sole upstream is feed processes / single-flight miss. Plan A2: “Not: a second Massive process unless Coach answers India’s finding.” The finding is: **do not start one.** Budget the union on pid 538.

This seat did not count live `mb:interest:mb:ladder:*` on StudioOne (read-only, and F0 did not SCAN). Foxtrot W4 / F1 **before 09:30 Tue** must state:

- topic count live-alone vs live+parallel covering keys;

- Massive standing connections: still **1** (`chain_feed`). Burst = one GET per interest topic per tick.

If the union cannot hold live 2s cadence, **slip Tuesday** or **restrict covering interest to SPX/XSP** (the named books). Do not add a Massive process.
